단서가 부족한 문장의 NED를 결합으로 해낸다

개체명 명확화(NED, Named Entity Disambiguation)는 문장 속 단어가 실제로 가리키는 대상을 지식베이스의 정확한 항목 하나로 연결하는 작업입니다.

출발점 — 7장 도구의 실패 지점

scispaCy가 놓치는 문장

  • scispaCy — spaCy 프레임워크 위에 만든 생물의학 전용 자연어 처리 도구
  • 표준 어휘집은 잘 활용하지만, 결정적인 단서 단어가 언급 바로 곁에 없으면 후보조차 찾지 못한다
  • 이 장은 바로 그 실패 지점에서 출발한다

이 장이 만드는 것

종단 간(end-to-end) NED 시스템

  • 범용 대규모 언어 모델(LLM) — 방대한 텍스트로 학습해 언어를 유창하게 생성·해석하는 인공지능 모델 — 을 로컬에 배포
  • 의학 온톨로지 SNOMED를 Neo4j 그래프로 적재
  • 둘을 엮어 종단 간 NED 시스템을 만든다

One Sentence — 문장의 의미 해석은 LLM에 맡기고 선택 가능한 개체와 관계의 근거는 도메인 온톨로지에서 가져오면, 주변 단서가 부족한 문장에서도 정확하고 설명 가능한 개체명 명확화를 해낼 수 있습니다.

교재 §8.1 · Motivation

8.1 전통적 NED 시스템의 한계 이해하기 — scispaCy가 놓치는 관계와 경로

scispaCy는 표준 어휘집으로 언급을 표준 개체에 연결하지만, 개체 사이에 이미 존재하는 관계와 경로는 쓰지 못한다.

01
AIML Quant교재 §8.1

표준 개체 목록이 있으면 표기가 달라도 하나로 묶인다

scispaCy는 UMLS(Unified Medical Language System, 통합 의학 용어 체계)처럼 표준화된 개체를 담은 어휘집과 온톨로지를 내장합니다.

표기 통일 문제

병원과 논문마다 다른 표현

"고혈압", "hypertension", "혈압이 높은 병"처럼 다르게 적힌 표현을 하나의 표준 개념 ID로 묶으면, 여러 기관의 데이터를 같은 기준으로 분석할 수 있습니다.

예를 이 장의 용어로

언급과 표준화된 개체

  • 서로 다른 세 표현 = 텍스트 속 언급(mention)
  • 이들이 모이는 표준 개념 ID = UMLS 같은 어휘집에 담긴 표준화된 개체
  • 표준 개체 목록을 갖추면 언급이 실제로 무엇을 가리키는지 정할 수 있어 모호함이 줄어든다

남는 질문 — 전문 사전을 갖고 있어도 사전 항목들이 서로 어떻게 연결되는지를 활용하지 못하면 판단력이 떨어집니다.

네 가지 한계

전통적 NED 도구의 약점

  1. 특정 응용 도메인, 곧 생물의학 분야에만 맞춰 설계되어 있다
  2. 새로운 개체와 용어를 반영하도록 참조 지식베이스를 확장하고 갱신하기 어렵다
  3. 지식베이스에 담긴 방대한 정보를 온전히 활용하지 못한다
  4. 개체 사이에 이미 존재하는 관계와 경로를 명확화 작업에 쓰지 못한다

관계가 판단을 바꾸는 예

Mercury — 수성, 수은, 자동차 브랜드

Mercury → IS_A → Planet · Mercury → ORBITS → Sun

  • 수성·수은·자동차 브랜드 = 지식베이스 안의 서로 다른 후보 개체
  • 두 관계 정보 = 전통적 NED가 쓰지 못하는 "개체 사이에 이미 존재하는 관계와 경로"

Mercury의 교훈 — 이름 문자열만 비교해서는 셋을 가르기 어렵지만, 저장된 관계를 보면 수성이라는 판단이 쉬워집니다.

class SnomedRelationshipsImporter(BaseImporter):
    def set_constraints(self):
        [...]   # id 유일성 제약과 이름·관계 속성 인덱스
    def import_snomed_rels(self):
        query = """
        UNWIND $batch as item
        MERGE (e1:SnomedEntity {id: item.sourceId})
        MERGE (e2:SnomedEntity {id: item.destinationId})
        MERGE (e1)-[:SNOMED_RELATION {id: item.typeId}]->(e2)
        FOREACH(ignoreMe IN CASE WHEN item.typeId = '116680003'
        THEN [true] ELSE [] END|
            MERGE (e1)-[:SNOMED_IS_A]->(e2))"""

코드 읽기

제약, MERGE, 그리고 116680003

  • set_constraints — id 유일성 제약은 같은 주민등록번호를 가진 사람을 두 명 등록하지 못하게 막는 규칙, 이름·관계 속성 인덱스는 책 뒤의 찾아보기처럼 검색을 빠르게 한다
  • MERGE — 데이터가 없으면 만들고 이미 있으면 기존 것을 재사용하는 명령
  • 116680003 — "A는 B의 한 종류다"라는 상위·하위(is-a) 관계의 SNOMED 코드. 이때만 SNOMED_IS_A를 추가로 만들며, 뒤의 계층 전파에서 핵심으로 쓰인다

두 벌의 관계 — "지카와 소두증이 어떻게 연결되는가?"는 SNOMED_RELATION으로, "소두증이 어느 상위 의료 범주에 속하는가?"는 SNOMED_IS_A로 탐색합니다. 전체 관계용 도로망과 계층 전용 도로망을 나눠 둔 셈입니다.

함께 나온 개체가 판단을 돕는다

  • Zika, 임신, 소두증, 선천성 기형이 한 문장에 함께 나오고 그래프에서도 서로 짧게 연결된다면 Congenital Zika virus infection을 고른다
  • 함께 나온 개체들 = 문맥 지식, 그래프에서 짧게 연결된다는 조건 = 최단 경로 탐지
  • 용어가 여러 의미나 연관을 가질 수 있는 복잡한 경우에 특히 효과가 크다

8.4.1 개체명 인식(NER) — 온톨로지가 정의한 범주로 개체 찾기

NER의 목표는 비정형 텍스트에 언급된 개체명을 찾아 Disease(질병), Organism(생물체), Procedure(시술) 같은 미리 정한 범주로 분류하는 것입니다.

두 질문의 차이

NER와 NED를 나란히 놓으면

  • NER — "문장에 어떤 이름이 있고, 대략 무슨 종류인가?"
  • NED — "그 이름은 지식베이스의 정확히 어느 항목인가?"

이 시나리오의 선택

SNOMED가 분류 기준을 고정한다

  • SNOMED의 구조화된 의학 지식을 끌어들여, LLM이 생물의학 텍스트에서 더 정밀하고 문맥을 아는 개체 인식을 수행하게 한다
  • "의학 개체를 알아서 분류하라"고 맡기는 대신 SNOMED가 인정하는 범주와 예시를 제공해 분류 기준을 고정한다

모델에게 주관식 대신 객관식을 준다

MATCH (n:SnomedEntity)
UNWIND n.type as named_entity
WITH DISTINCT named_entity,
     count(named_entity) as num_of_entities
ORDER BY num_of_entities DESC
RETURN collect(named_entity) as named_entities

위치는 파이썬이 끝까지 센다

문자열 안에서 부분 문자열이 나타나는 모든 위치를 찾아, 시작·끝 인덱스 튜플을 모아 돌려주는 함수입니다.

def find_all_mention_indices(self, string, substring):
    indices = []
    start_index = 0
    while True:
        start_index = string.find(substring, start_index)
        if start_index == -1:
            break  # No more occurrences found
        end_index = start_index + len(substring) - 1
        indices.append((start_index, end_index))
        #### Move start_index forward to search for the next occurrence
        start_index += len(substring)
    return indices

$labels가 탐색을 좁히고 ~0.80이 변형을 허용한다

쿼리의 $labels 매개변수와 각 단어 뒤의 ~0.80이 검색의 폭을 결정합니다.

def generate_full_text_query(self, input):
    full_text_query = ""
    words = [el for el in input.split() if el]
    if len(words) > 1:
        for word in words[:-1]:
            full_text_query += f" {word}~0.80 AND "
        full_text_query += f" {words[-1]}~0.80"
    else:
        full_text_query = words[0] + "~0.80"
    return full_text_query.strip()

두 장치

좁히기와 허용하기

  • $labels — NER 단계의 출력에서 모은 라벨로, 언급된 개체 유형과 관련 있는 개체의 부분집합만 찾도록 검색을 좁힌다. cold의 라벨이 Disease라면 "감기" 쪽에서, Temperature라면 "낮은 온도" 쪽에서 찾는다
  • ~0.80 — 퍼지 매칭(fuzzy matching). 철자가 조금 다르거나 변형된 형태라도 유사도 0.80 이상이면 후보로 잡는다
  • 기준의 양쪽 경계 — 너무 낮추면 무관한 후보가 늘고, 너무 높이면 오탈자나 변형 표현을 놓친다

원서 NOTE — 벡터 기반 검색을 함께 쓰면 문자 매칭으로 잡히지 않는 추가 후보까지 끌어올 수 있습니다. heart attack과 myocardial infarction처럼 글자 모양은 다르지만 뜻이 같은 짝이 그 예입니다. 전문 검색은 철자 유사성에, 벡터 검색은 의미 유사성에 강합니다.

    WHERE s1.id="{s1_id}" AND
          s2.id="{s2_id}"

             AS paths,

  • 속성 경로 — [:PATHOLOGICAL_PROCESS_(ATTRIBUTE)]는 두 개념이 병리 과정 속성을 공유함을 나타낸다
  • 각 경로는 온톨로지 안의 동시 출현을 근거로 생물의학 개체 사이의 관계적 연결을 보여 준다

그래프 기호를 LLM에게 익숙한 언어로 번역한다

LLM은 그래프 기호보다 "A는 B와 이런 관계가 있다"라는 문장을 더 안정적으로 해석하므로, 그래프 알고리즘의 결과를 LLM에게 익숙한 언어로 번역해 줍니다.

system = """You are an assistant capable of translating a Neo4j
graph path into a clear sentence.
Use the exact entity names from the path [...]"""
input = {
    "path": "
        (Hypertension)-[:RISK_FACTOR_FOR]->(Cardiovascular Disease)
        <-[:ASSOCIATED_WITH]-(Myocardial Infarction)"
}
assistant = {
    "sentence": "Hypertension is a risk factor for
cardiovascular disease. Myocardial infarction is also
associated with cardiovascular disease, [...]"
}

프롬프트 읽기

이름은 정확히, 문장은 자연스럽게

  • system — 경로를 명확한 문장으로 옮기되, 경로에 나온 정확한 개체 이름을 그대로 쓰라고 요구한다
  • 이름 보존의 이유 — 변환 과정에서 개체 이름을 비슷한 표현으로 바꿔 버리면 나중에 원래 후보 ID와 다시 연결하기 어려워질 수 있다
  • assistant 예시 — 그래프 고혈압 → 심혈관질환 ← 심근경색이 "고혈압은 심혈관질환의 위험 요인이며 심근경색도 심혈관질환과 관련된다"라는 문장으로 바뀐다
  • 결과를 JSON으로 감싸는 이유 — 다음 프로그램이 출력을 안정적으로 읽게 하기 위해서다

  • 목표는 무조건 짧게가 아니다 — 최종 후보를 구별하는 데 필요한 개체명·관계 유형·관계 방향은 요약에 남아야 한다. 지나치게 압축하면 결정의 근거 자체가 사라질 수 있다
  • 입력은 고혈압·당뇨병·천식·골다공증 관련 네 문장, 출력은 이를 묶은 하나의 매끄러운 문맥 문단이다

disambiguation.
Your task is to identify and accurately disambiguate the
entities mentioned in a given sentence, relying heavily on the

entities that need to be resolved.
2. Candidate Entities: A list of potential entities extracted
from the sentence, with each entity having multiple possible

  • 개체명 명확화는 복잡한 도메인에서 개체를 정확히 식별하고 구별하는 데 필수적이다
  • scispaCy 같은 전통적 NLP 도구는 다양한 도메인에 쓸 수 없고, 개체 사이의 관계를 활용하지 못하며, 참조 지식을 확장하고 갱신하기도 어렵다
  • 범용 LLM과 도메인 온톨로지를 결합하면 이 문제들을 해소할 수 있다 — LLM은 온톨로지의 끊임없이 갱신되는 지식의 인도를 받으며 그 관계 구조를 활용할 수 있다

구현과 전망

무엇을 만들었는가

  • 저자들은 LLM과 도메인 온톨로지가 여러 단계에서 맞물리는 유연한 종단 간 NED 과정을 배포했다
  • LLM의 능력과 온톨로지의 그래프 차원을 온전히 쓰기 위해 명확화를 세 단계 — 최단 경로 탐지, 경로-텍스트 변환, 텍스트 경로 요약 — 로 나눴다
  • 미래의 NED 응용은 이 프레임워크를 써서, 개체의 관계적 성질을 기술하는 풍부한 온톨로지를 갖춘 다른 도메인에도 적응할 수 있다

Final Takeaway — 텍스트의 의미는 LLM이 해석하되 선택 가능한 개체와 관계의 근거는 도메인 온톨로지에서 가져오면, 더 정확하고 설명 가능한 NED 시스템을 만들 수 있습니다.

라벨과 경로의 지위

결과를 읽는 경계

  • NER 라벨은 최종 개체가 아니다 — Zika → Organism은 초기 분류이고 Zika → SNOMED 762725007이 최종 연결이다. 초기 라벨을 결과로 보고하면 안 된다
  • 최단 경로가 인과관계를 증명하지는 않는다 — 그래프에서 가깝다는 것은 관련성의 단서일 뿐, 관계 유형과 방향을 반드시 함께 봐야 한다
  • 경로를 문장으로 바꿀 때 의미를 키우면 안 된다 — ASSOCIATED_WITH를 "유발한다"로 옮기는 순간 원래 지식보다 강한 주장이 된다

  • 온톨로지 품질이 결과의 상한선을 정한다 — 후보나 관계가 없거나 오래됐다면 LLM도 올바른 근거를 얻을 수 없다
